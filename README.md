# Лаб 2: Гүйцэтгэлийн хэмжүүрийг k6-аар хэмжих

Нэр: О.Хүслэн
Оюутны код: B242270073
F.CSA313 — Программ хангамжийн чанарын баталгаа ба тест (2026)

## Орчин
```
k6 v0.55.0 (commit/90bb9415d0, go1.23.3, linux/amd64)
```
- OS:  Linux, Node.js + Express (локал сервер)

## Ёс зүй
Тестийг зөвхөн өөрийн локал машин дээр ажиллуулсан сервер (`http://localhost:3000`) рүү хийсэн. Гадаад болон сургуулийн сайт руу тест хийгээгүй.

## Тестийн бай (server.js)
- `GET /work` — ~100 мс боловсруулалттай удаан endpoint. Нэгэн зэрэг хамгийн ихдээ 8 хүсэлт боловсруулдаг, илүүдэл нь дараалалд хүлээнэ. Теоретик багтаамж ≈ 8 / 0.1 с = ~80 хүсэлт/сек.
- `GET /fast` — хурдан endpoint (харьцуулалтад).

## Файлууд
- `server.js` — локал сервер
- `script.js` — үндсэн тест (stages-гүй, VU-г `--vus`-аар өгнө)
- `stages.js` — шатлан өсгөх тест (5 → 30 → 100 → 0)
- `slo-pass.js` — SLO threshold (PASS)
- `slo-fail.js` — зориуд хатуу threshold (FAIL)
- `results/` — k6-ийн бүтэн текст гаралтууд
- `screenshots/` — k6 summary-ийн дэлгэцийн зургууд

## Ажиллуулах
```bash
npm install express
node server.js        # нэг терминал дээр
mkdir -p results
k6 run --vus 5   --duration 1m script.js | tee results/run-05vu.txt
k6 run --vus 30  --duration 1m script.js | tee results/run-30vu.txt
k6 run --vus 100 --duration 1m script.js | tee results/run-100vu.txt
k6 run stages.js    | tee results/run-stages.txt
k6 run slo-pass.js  | tee results/slo-pass.txt
k6 run slo-fail.js  | tee results/slo-fail.txt
```

Stages хувилбар (results/run-stages.txt): нийт p95 = 217.77 мс, throughput 27.33 req/s, error rate 0.00%. Ачаалал өсөх үед p95 нэмэгдэж, буух үед буурсныг ажигласан. Энэ нь нэгтгэсэн нэг summary тул хүснэгтийн тоог дээрх гурван тусдаа ажиллуулалтаас авсан.

## SLO ба threshold
Baseline нь 5 VU-ийн p95 = **104.82 мс**. SLO-г үүнээс гаргасан:
- **p(95) < 157 мс** (104.82 × 1.5)
- **error rate < 1%**

**Үндэслэл:** Baseline-аас 1.5 дахин хүртэл нөөц үлдээснээр жижиг хэлбэлзлийг (хамгийн ихдээ ~110 мс гарсан) хүлээн авна. Харин серверийн багтаамж дүүрч дарааллын хугацаа нэмэгдэх үед (100 VU дээр 309 мс) бодитоор зөрчигдөнө, тиймээс threshold нь утга учиртай.

| Туршилт | Threshold | Бодит p95 | Дүн | Файл |
|---|---|---|---|---|
| slo-pass.js (30 VU) | p(95)<157, error<1% | 109.93 мс | **PASS** (exit=0) | results/slo-pass.txt |
| slo-fail.js (30 VU) | p(95)<50 (зориуд) | 107.41 мс | **FAIL** (exit=99) | results/slo-fail.txt |

FAIL үед k6 нь "thresholds ... have been crossed" гэж мэдээлж, exit code 99 буцаасан. CI pipeline дээр quality gate яг ийм зарчмаар ажилладаг.

## Дүгнэлт
Ачаалал 5 VU-аас 30 VU болоход p95 latency 104.82 мс-ээс 106.30 мс болж бараг өөрчлөгдөөгүй, харин throughput 4.53-аас 27.04 req/s болж ойролцоогоор VU-тэй пропорциональ өссөн. Энэ үед сервер багтаамжаасаа хол байсан тул хэрэглэгчийн туршлага муудаагүй. 100 VU дээр throughput 77.99 req/s болж серверийн ~80 req/s багтаамжид хүрсэн бөгөөд p95 нь 308.97 мс болж baseline-аас ойролцоогоор 3 дахин өссөн. Өөрөөр хэлбэл 30 VU-аас 100 VU хооронд хаа нэгтээ "нэгж хэрэглэгчийн туршлага" муудаж эхэлсэн бөгөөд энэ нь серверийн дарааллын хугацаа нэмэгдсэнтэй холбоотой. Энэ нь лекцэд үзсэн "хэрэглэгч олширвол latency өснө, throughput дээд хязгаартаа тогтдог" зөрчлийг батлав. Error rate бүх түвшинд 0% байсан тул зөвхөн error rate харвал систем эрүүл мэт харагдах боловч latency-д асуудал илэрсэн нь нэг хэмжүүрт найдаж болохгүйг харуулсан. p95 нь avg-аас (267 мс) илүү сайн хойд хэсгийн удаашралыг илрүүлдэг тул SLO-д p95-г сонгосон нь зөв байлаа. Минийхээр SLO нь p95 < 157 мс, error rate < 1% байсан бөгөөд 30 VU дээр p95 = 109.93 мс байж хангагдсан. 100 VU дээр p95 309 мс тул энэ SLO зөрчигдөх байсан. Зориуд p(95)<50 болгоход тест FAIL болж exit code 99 өгсөн нь threshold-ыг автомат quality gate болгож болдгийг харуулав. Цаашид серверийн worker-ийн тоог нэмэх, эсвэл ачааллыг хязгаарлах замаар 100 VU дээр SLO-г хангах боломжтой.
